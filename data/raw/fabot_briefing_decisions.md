# DECISIONS — FABOT 데일리 브리핑 에이전트

카드뉴스 실습(Day 39)에서와 같은 방식으로, 구현 전에 정할 것을 여기 기록한다.

## D01. 실행 엔진 — CHOSEN: Claude Agent SDK

- 이 컴퓨터에 이미 설치·로그인된 `claude` CLI(Claude Code 2.1.241)를 그대로 재사용함 —
  console.anthropic.com API 키를 새로 발급받을 필요 없음(그때 실패했던 카드결제와 무관한
  별도 로그인). SDK가 내부적으로 `claude` CLI를 호출하는 방식이라 추가 인증 불필요.
- Ollama(qwen3.5:2b)보다 응답 품질이 높아, 매번 다른 자연어 리포트를 써야 하는 이 작업에
  더 적합함.
- **주의**: npm으로 설치된 `claude.cmd`는 SDK가 보안상(cmd.exe 인젝션 위험) 실행을 거부함 →
  공식 네이티브 설치 스크립트(`irm https://claude.ai/install.ps1 | iex`)로 `claude.exe`를
  별도 설치(PATH 미등록, `cli_path` 옵션으로 직접 지정).
- **실제 호출 검증 완료**(2026-09-09): `test_sdk_connection.py`로 "7+8=?" 질문 → "15" 정답 수신.
  API 키 없이 이 Claude Code 로그인으로 과금됨(`apiKeySource: none`).
- **비용 메모**: 테스트 1건에 $0.13 — 대부분 최초 캐시 생성 비용(1시간 캐시, 32,913토큰).
  매일 새 세션으로 실행하면 캐시가 매번 새로 생성될 수 있음 → 실제 일일 비용은 운영 중
  토큰 로그로 확인 필요(PRD 7절 평가 계획에 이미 포함).

## D02. 구현 언어 — CHOSEN: Python

- harness-design-kit, fabot-auto-trade, fg-index 전부 Python이라 코드·경험 재사용 가능
- `claude-agent-sdk` 파이썬 패키지 사용

## D03. 배포 플랫폼 — CHOSEN: Render (Docker, 무료 플랜)

- 기존 fabot-trade-journal과 동일 플랫폼(Render) 사용.
- Docker 런타임 사용 — Claude Agent SDK가 필요로 하는 `claude` CLI(Node 기반, npm 설치)를
  빌드 시점에 확실히 설치하기 위함.
- **무료 플랜 선택**(2026-09-09, 사용자 확인) — 유료 디스크($7/월) 없이 시작.
- **2026-09-10 업데이트**: 실제로 재배포할 때마다 실행 이력이 사라지는 걸 사용자가
  직접 겪고 지적함 → 로컬 SQLite(`executions.db`) 대신 **Supabase**(`briefing_executions`
  테이블, 기존 FABOT 프로젝트와 동일)로 상태 저장소를 옮김(store.py). 유료 디스크 없이도
  이력이 영구 보존되고, 다른 FABOT 서비스들과 인프라를 통일하는 효과도 있음. 카드 이미지는
  Storage 버킷 대신 base64 텍스트 컬럼에 그대로 저장(카드 1장 ~100KB, 발송 빈도가 낮아
  단순함을 택함 — 트래픽이 커지면 재검토).
- 인증: `CLAUDE_CODE_OAUTH_TOKEN`(로컬에서 `claude setup-token`으로 생성, 구독 기반
  장기 토큰) — 이 서버 환경에는 대화형 로그인이 불가능해서 로컬 CLI 로그인 재사용(D01)
  방식을 그대로 쓸 수 없기 때문. API 키 결제 문제와는 무관한 별도 경로.
- **실제로 겪은 오류(2026-09-09)**: 컨테이너가 기본 root로 실행되는데, Claude CLI가
  `permission_mode="bypassPermissions"`가 내부적으로 쓰는 `--dangerously-skip-permissions`를
  보안상 root에서 거부함(Render 로그로 직접 확인). Dockerfile에 비-root 사용자를 추가해
  해결, 재배포 후 실제 브리핑 생성→승인→발송까지 배포 서버에서 확인함.

## D04. 카드뉴스 이미지 출처 — CHOSEN: Pexels 무료 스톡 사진

카드뉴스 실습(Day 39)이 권장한 3가지 이미지 출처(CC0/퍼블릭 도메인, 라이선스 허용 스톡,
생성 이미지) 중 하나를 순서대로 실제 시도해보고 결정함:

1. **Antigravity CLI(강의 참고 구현)**: 이 컴퓨터에 설치 안 되어 있었고, 별도 계정·설치가
   필요해 보류.
2. **Gemini 이미지 API 직접 호출(Antigravity가 내부적으로 쓰는 모델을 그대로 호출)**:
   설치는 필요 없지만, 실제로 호출해보니 무료 할당량이 0으로 확인됨(HTTP 429, "limit: 0")
   — 결제 계정 연결이 필요함. Anthropic API 콘솔 때와 같은 종류의 결제 장벽이라 사용자가
   보류를 선택함(2026-09-09).
3. **Pexels 스톡 사진 검색 — 최종 선택**: 무료 API 키 발급에 카드 등록 불필요, 실제 검색·
   다운로드까지 검증 완료. 에이전트가 만든 영어 검색 키워드로 `tools_impl.search_stock_photo()`가
   실시간 검색하고, 사진작가·출처 URL을 캡션에 항상 남긴다(실습이 요구한 출처 기록 원칙).

## D05. 스케줄 브리핑 승인 정책 — CHOSEN: 자동 발송(승인 생략)

하루 4번(미국장 마감 07:00 / 한국장 개장 08:00 / 한국장 마감 16:00 / 미국장 개장 22:00,
전부 KST) 도는 시황 카드뉴스는, 사람이 승인해야만 발송되는 기존 데일리 브리핑(D06,
PRD 5절)과 달리 **생성 즉시 자동으로 텔레그램에 발송**한다. 일상적인 시황 정보를 매번
승인받는 건 비현실적이라는 사용자 판단(2026-09-09). 대신:
- 도구는 여전히 읽기 전용 2개뿐(발송 도구는 에이전트에 노출 안 함, D06 원칙 유지)
- 외부에서 아무나 호출하면 실제 발송·API 비용이 발생하므로, `/api/scheduled/{session}`
  엔드포인트는 `SCHEDULE_SECRET` 비밀 토큰으로 보호함
- 실행 이력은 웹 화면에도 남아 사후에 확인 가능(카드 이미지 포함)

## D06. FABOT 계좌 알림과 시장 카드뉴스 분리 — CHOSEN: 별도 메시지

2026-09-10 사용자 요청: 카드뉴스를 쉬운 말로 바꾸다 보니 F&G 수치·쿨다운 같은 정확한
계좌 신호 정보가 뭉개질 위험이 생김. 그래서 스케줄 브리핑마다 텔레그램 메시지를 2개로
분리함:
1. **FABOT 시스템 알림**(텍스트) — `tools_impl.build_fabot_status_alert()`가 실제 조회
   결과를 그대로 문자열로 조립(LLM 미사용, 숫자 왜곡 위험 없음). 기존 `balance_watchdog.py`
   등 FABOT 알림과 같은 "정확한 사실 그대로" 톤 유지.
2. **시장 카드뉴스**(사진) — 기존과 동일, 쉬운 말 + 분위기에 맞는 스톡 사진.
두 메시지 다 승인 없이 자동 발송됨(D05와 동일 정책).

## D07. 알림 분류 표시 — CHOSEN: 한 채팅방 + 이모지 제목 규칙

2026-09-10 사용자 요청: 채팅방을 여러 개로 나누면 관리 부담이 커지니, **하나의
채팅방**을 유지하되 메시지 맨 앞에 카테고리를 항상 명시하기로 함:
- `🤖 FABOT 시스템` — 계좌/신호 관련 정확한 정보(정기 시스템 알림 + 수동 승인 브리핑)
- `📊 증시 브리핑` — **내 계좌와 완전히 무관한, 시장 전체 분위기만** 담은 쉬운 말 카드뉴스.
  2026-09-10 사용자 지적으로 발견: 처음엔 카드에 커버드콜 매수·쿨다운 같은 계좌 얘기가
  섞여 있었음 → `market_briefing.py`에서 `fabot_query_trade_history` 도구 자체를
  빼서(프롬프트로만 막지 않고 구조적으로) 재발 방지
- `📰 주요 뉴스` — 아직 미구현. 실시간 뉴스 검색 도구가 없어서 별도 개발 필요(다음 확장).

대안으로 텔레그램 Topics(포럼 그룹)도 검토했으나, 지금 쓰는 1:1 봇 채팅을 그룹으로
바꾸고 Topics를 켜야 해서 설정 부담이 커 보류함.

## D08. F&G 데이터 소스 우선순위 — CHOSEN: 실제 CNN 원본 우선, 가격 역산 지표는 보조

2026-09-10 사용자 요청: "실제 CNN F&G 데이터를 쓰고 싶다. 가격 역산으로 계산한 F&G는
6개월~1년 정도 실측 대조 검증이 되기 전까지는 신뢰하지 말자."

- `fg-index` 프로젝트가 이미 CNN 공식 API에서 실제 원본 점수를 매일 받아 Supabase
  `live_scores` 테이블에 `source='cnn_real'`로 쌓고 있었음(2026-07-16부터, 현재
  70,715건 이상) — CLAUDE.md의 "다음 단계" ①번(CNN 원본 데이터 확보)이 이미 별도
  프로젝트에서 완료돼 있던 것을 이번에 브리핑 에이전트에 연결함.
- `tools_impl.py`에 `_get_cnn_real_score()` 추가 — `live_scores`에서 `source=cnn_real`
  최신 행을 직접 조회.
- `query_fg_signal()`의 점수 소스 우선순위를 다음처럼 변경:
  1. **실제 CNN 원본**(`_get_cnn_real_score()`) — 우선 사용
  2. 가격 역산 실시간 지표(`today_signal.get_realtime_score()`, `source='price_based'`)
     — CNN 원본 조회 실패 시에만 폴백
  3. `today_signal` 내부의 로컬 CSV 스냅샷(stale) — 위 둘 다 실패할 때만
- **원칙 확정(중요)**: 가격에서 역산한 `price_based` 지표는 계산 방법론일 뿐 실측
  검증이 안 된 상태 — 최소 6개월~1년 실제 CNN 값과 나란히 대조해서 상관관계·오차범위가
  검증되기 전까지는 **실거래 매수/매도 신호로 쓰지 않는다**. 지금은 CNN 원본 조회가
  실패했을 때만 쓰는 비상 폴백 용도로 격하함.
- 로컬 검증(2026-09-10): `query_fg_signal()` 실행 결과
  `{'score': 38.89, 'rating': 'realtime_cnn_real', 'days_old': 0, 'effectively_stale': False}`
  — 실제 CNN 데이터가 정상적으로 흘러 들어옴을 확인.
