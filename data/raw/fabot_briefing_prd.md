## 1. 문제 정의

**반복 업무**: 매일(또는 필요할 때마다), FABOT 자동매매 계좌(KIS·키움)의 최근 매매·배당 기록과
현재 F&G(공포탐욕) 지수를 직접 대시보드·DB에서 찾아보고, "지금 상황이 어떤지, 다음엔 어떤
매매 신호가 예상되는지"를 스스로 정리해야 한다. 여기에 더해 "오늘 시장 전체 분위기는 어떤지"도
매번 뉴스를 따로 찾아봐야 한다.

**왜 규칙 기반 스크립트가 아니라 에이전트가 필요한가**: `auto_trade_loop.py`는 이미 "매매가
실행됐을 때" 결과를 텔레그램으로 보낸다(규칙 기반, 고정된 문구). 이 시스템은 그와 달리
**매매가 없었던 날에도** 여러 출처(DB, F&G 지수, 실시간 뉴스)의 정보를 조합해서 **매번 다른,
자연어로 된 설명**을 만들어야 하므로 LLM의 판단·작문·검색이 필요하다.

## 2. 타겟 유저

- 1차: 본인(조아라) — FABOT 운영자, 매일 계좌 상황과 시장 분위기를 파악하고 싶어함
- 확장 가능: 배당 분산 대상인 가족 구성원(가족구성원B 등)에게도 요약 공유 가능(MVP 범위 밖)

## 3. 전체 구조 — 4가지 발송 경로

실제로 만들고 보니, "브리핑"이 하나가 아니라 성격이 다른 4가지 발송 경로로 나뉘었다.
전부 텔레그램 한 채팅방으로 가되, 메시지 맨 앞에 카테고리를 붙여 구분한다(D07).

| 경로 | 트리거 | 내용 출처 | 사람 개입 | 라벨 |
|---|---|---|---|---|
| ① AI 초안 작성 | 웹 화면 "브리핑 생성" 버튼 | 실제 계좌 데이터(에이전트가 도구로 조회) | 승인 필수(직접 수정도 가능) | 🤖 FABOT 시스템 |
| ② 직접 작성 | 웹 화면에 사람이 직접 타이핑 | 사람이 쓴 그대로 | 쓰는 행위 자체가 승인 | 🤖 FABOT 시스템 |
| ③ 자동 시황 카드뉴스 | cron-job.org, 하루 4번 | 실시간 웹 검색(진짜 뉴스) | 없음(자동 발송) | 📊 증시 브리핑 |
| ④ FABOT 시스템 알림 | ③과 같은 트리거, 카드 직전 발송 | 실제 F&G/쿨다운 수치(LLM 미개입, 그대로 조립) | 없음(자동 발송) | 🤖 FABOT 시스템 |

**핵심 설계 원칙 하나**: F&G 지수·매매 신호·쿨다운처럼 "정확해야 하는 계좌 정보"와,
"오늘 시장이 대체로 어떤 분위기인지"는 서로 다른 것으로 취급한다(2026-09-10 사용자 지적).
그래서 ③(시장 카드뉴스)에는 계좌 관련 도구를 아예 노출하지 않고, ④(시스템 알림)는
LLM이 아니라 실제 조회 결과를 그대로 문자열로 조립해서 숫자가 왜곡될 여지를 없앴다.

## 4. 워크플로 상세

### ① AI 초안 작성

| 단계 | 내용 | 주체 |
|---|---|---|
| 1. 트리거 | "브리핑 생성" 버튼 클릭 | 사람 |
| 2. 계획 | 어떤 기간의 매매기록을 볼지 판단 | 에이전트 |
| 3. 도구 호출 | `fabot_query_trade_history`, `fabot_query_fg_signal` | 도구 |
| 4. 작성 | 조회 결과로 자연어 리포트 작성 | 에이전트 |
| 5. 검토·수정 | 화면에서 내용을 직접 고칠 수 있음(2026-09-10 추가) | 사람 |
| 6. 결정 | 승인 / AI에게 재작성 요청 / 거절 | 사람 |
| 7. 발송 | 승인된 텍스트를 텔레그램으로 | 도구 |

**진행 상황 실시간 표시**(2026-09-10 추가): 완료까지 15~20초 걸리는데 그동안 화면이
안 바뀌면 멈춘 것처럼 보인다는 지적에 따라, 도구 호출·추론 이벤트를 생기는 즉시 저장해서
화면이 실시간으로 갱신되게 함.

**직접 편집**(2026-09-10 추가): "승인 대기 중" 상태의 초안은 텍스트박스가 편집 가능해지고,
고친 내용 그대로 승인하면 그게 발송된다 — AI에게 다시 써달라고 요청하지 않고 사람이
바로 손볼 수 있음.

### ② 직접 작성

사람이 처음부터 끝까지 쓴 내용을 승인 절차 없이 바로 발송한다(쓰는 것 자체가 승인).
AI가 전혀 개입하지 않아 속도가 빠르고, 짧은 공지성 메시지에 적합.

### ③ 자동 시황 카드뉴스 (하루 4번)

- **트리거**: cron-job.org → `POST /api/scheduled/{session}?token=...` (`us_close` 07:00,
  `kr_open` 08:00, `kr_close` 16:00, `us_open` 22:00, 전부 KST)
- **내용**: Claude Code 내장 **WebSearch**로 그 시간대에 맞는 실제 시장 뉴스를 검색해서
  쉬운 말로 요약. 계좌·F&G 정보는 다루지 않음(③④ 분리 원칙).
- **이미지**: Pexels 무료 스톡 사진 검색(D04) — 본문 분위기(하락/상승/평온)에 맞는 영어
  키워드로 검색, 출처를 캡션에 항상 표기.
- **콜드스타트 대응**: 응답은 즉시 보내고 실제 생성은 백그라운드에서(cron-job.org
  타임아웃 30초 vs Render 무료 인스턴스 기상 시간 최대 50초 문제 대응) + keepalive
  cron(10분마다 핑)으로 아예 잠들지 않게 함.

### ④ FABOT 시스템 알림 (③ 직전에 같이 발송)

`tools_impl.build_fabot_status_alert()`가 실제 F&G 점수·최종 신호를 LLM 없이 그대로
문자열로 조립한다 — 숫자가 요약 과정에서 왜곡될 위험을 원천 차단.

## 5. 도구 계획

| 도구 | 하는 일 | 권한 | 노출 대상 |
|---|---|---|---|
| `query_trade_history` | Supabase `trades` 테이블에서 최근 N일 매매·배당 조회 | 읽기 전용 | ① |
| `query_fg_signal` | 실시간 F&G 지수 + FABOT 신호(쿨다운 반영) 조회 | 읽기 전용 | ①④ |
| `WebSearch` | 실제 시장 뉴스 검색(Claude Code 내장) | 읽기 전용 | ③ |
| `search_stock_photo` | Pexels 무료 스톡 사진 검색 | 읽기 전용 | ③ |
| `send_telegram` / `send_telegram_photo` | 텔레그램 발송 | **쓰기(발송)** | 에이전트에는 절대 미노출 |

**핵심 안전장치(D06)**: 발송 도구(`send_telegram*`)는 어떤 에이전트에도 노출하지 않는다.
①은 사람이 승인 버튼을 눌러야만, ③④는 서버 코드가 생성 완료 후 직접 호출하는 경로로만
실행된다 — 에이전트가 스스로 발송을 트리거할 코드 경로 자체가 없다.

**실패 처리 규칙**:
- DB/F&G 조회 실패 → 리포트에 "조회 실패로 반영 못함"을 명시(숨기지 않음)
- 텔레그램 발송 실패 → 화면에 "발송 실패" 표시 + 재시도 버튼(내용을 고쳐서 재시도도 가능)

## 6. 사람 개입 지점

|---|---|---|

## 11. 다음에 더 신경 써야 할 것 (2026-09-10, 만들고 나서 돌아본 평가)

시스템이 어느 정도 굴러가긴 하는데, 실제로 운영을 계속하려면 아래를 순서대로 보는 게
좋겠다고 판단한 이유를 남긴다.

### 지금 당장 — 보안: 화면에 아무 보호장치가 없음

`https://fabot-daily-briefing-agent.onrender.com` 주소를 아는 사람은 **누구나**:
- 내 실제 계좌(총자산·보유종목·매매내역)를 볼 수 있고
- "브리핑 생성"·"직접 작성해서 보내기"를 눌러 **내 텔레그램으로 메시지를 보낼 수 있음**

③④(스케줄) 엔드포인트만 비밀 토큰으로 막혀 있고, 웹 화면 자체(①②, 이력 조회)는 무방비다.
**가장 간단한 해결책**: 이 앱 전체에 비밀번호 하나(Basic Auth 또는 접속 시 암호 입력)를
걸어두는 것.

### 이번에 실제로 고친 것 — F&G가 배포 시점에 멈춰있던 문제

방금 고쳤지만 기록으로 남긴다: `get_today_score()`가 배포할 때 같이 올라간 정적 파일을
읽어서, 배포 이후로는 며칠이 지나도 절대 안 바뀌는 값을 계속 보여주고 있었다. 이미 있던
`live_scores`(fg-dashboard가 5분마다 갱신) 테이블로 바꿔서 해결함. **비슷한 종류의
"한 번 굳으면 안 바뀌는 값"이 또 있는지 주기적으로 의심해볼 것.**

### 다음으로 — 비용 추적

에이전트 호출 1건당 실제 비용이 든다(AI 초안 1회 $0.04~0.17, 카드뉴스도 검색+생성
비용 있음). 지금은 실행 1건씩 `usage.total_cost_usd`는 기록되지만, **누적 얼마 썼는지
한눈에 보는 화면이 없다.** 하루 4번(자동) + 수시(수동) 다 더하면 한 달이면 꽤 쌓일 수
있어서, 화면에 "이번 달 누적 비용" 정도는 보여주는 게 좋겠다.

### 다음으로 — 스케줄이 실제로 다 도는지 아무도 감시 안 함

`balance_watchdog.py`가 잔고 기록 공백을 감시하듯, 이 시스템의 하루 4번 스케줄도
"오늘 4번 다 왔어야 하는데 안 왔다"를 감지하는 장치가 없다. Render가 죽거나
cron-job.org가 실패해도 조용히 넘어간다 — 알아채는 유일한 방법이 "어? 오늘 카드
안 왔네" 하고 사람이 눈치채는 것뿐이다.

### 여유 있을 때 — 평가 커버리지 최신화

EVAL_RESULTS.md는 ①(AI 초안)만 다룬다. 이후 추가된 ②③④(직접 작성, 시황 카드뉴스,
시스템 알림)는 개별적으로 실제 발송 확인은 했지만, PRD 9절 같은 "시나리오 표"로
정리된 적은 없다. 급하지 않지만, 과제 제출/향후 회고용으로 정리해두면 좋음.
