# 평가 시나리오 결과 (PRD 7절)

5개 시나리오 실행 결과. 실제 조건을 강제로 만들 수 없는 2개(F&G 극단값, DB 조회 실패)는
도구 결과 한 지점만 모의(mock)로 바꾸고, 에이전트 호출부터 리포트 작성까지 나머지는 전부
실제로 실행했다 — 어디를 모의했는지 표에 그대로 남긴다.

| # | 시나리오 | 모의 여부 | 기대 결과 | 실제 결과 | 통과 |
|---|---|---|---|---|---|
| 1 | 최근 매매가 있었던 날 | 아니오(실제) | 실제 매매 내역이 리포트에 반영 | 2026-09-09 최초 실행에서 08-28 매수 건이 정확히 반영됨 (README 참고) | ✅ |
| 2 | 최근 매매 없음 | 도구 결과 1곳만 모의 | "최근 N일간 매매 없음" 명시 | 정확히 명시함. **덤으로**: 모의 안 한 F&G 도구가 자체 조회한 실제 쿨다운 정보(마지막 매수 09-09)와 모의된 "매매 없음"이 서로 다르다는 걸 에이전트가 스스로 알아채고 "데이터 정합성 확인 필요"라고 경고까지 넣음 | ✅ |
| 3 | F&G 극단값(공포 15점) | `get_today_score()` 반환값만 모의 | "매수 100%"급 신호와 15점이 리포트에 등장 | 15점·매수 신호 정상 반영 (F&G 계산 로직 자체는 건드리지 않음) | ✅ |
| 4 | DB(Supabase) 조회 실패 | `query_trade_history` 강제 실패 | 실패를 숨기지 않고 "조회 실패로 반영 못함" 명시 | 정확히 명시하고, 나머지(F&G) 정보로는 계속 리포트 작성 — 전체를 포기하지 않음 | ✅ |
| 5 | 사람이 거절/수정 요청 | 아니오(실제 서버) | 거절 시 발송 안 됨, 수정 요청 시 반영해 재작성 | 실제 서버로 실행: "더 짧게, 2문장으로만 요약해줘" 요청 → 정확히 2문장으로 재작성됨. 별도 실행을 거절 → `status: rejected`, `sent_at: null` 확인. 이미 `done`인 실행에 승인을 다시 호출해도 `sent_at`이 그대로라 재발송 안 됨(멱등성) 확인 | ✅ |

실행 스크립트: eval_scenarios.py, 원시 결과: eval_results.json.

## 발견한 것

에이전트가 "매매 없음"이라는 (모의로 주입된) 정보와, 별도 도구가 실제로 조회해온 쿨다운
정보가 서로 모순된다는 것을 스스로 감지하고 사람에게 알렸다 — 지시하지 않은 동작이다.
이건 두 도구를 각각 독립적으로 호출하게 설계했기 때문에 가능했던 것으로 보인다(한 도구
결과를 그대로 요약만 하는 구조였다면 이 모순을 잡아내지 못했을 것).
